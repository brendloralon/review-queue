# CLAUDE.md

Shared conventions for the Review Queue app. Stack rules live in `backend/CLAUDE.md` (generated by Laravel Boost from `backend/.ai/guidelines/`) and `frontend/AGENTS.md`.

**Precedence:** these project rules override generated framework guidance. If a request conflicts with a rule, say so instead of silently breaking it.

## Product

A reviewer works through a queue of submitted items.
- Anyone can submit an item.
- On submission, moderation heuristics compute a risk score, flags, and a suggested action. They inform the reviewer only; they never block submission or decide.
- A reviewer opens an item, approves or rejects it, and can leave an optional note.
- The queue can be browsed by status, searched, and sorted.

**Scope:** the above, plus at most one stretch goal chosen after the core is complete (logged in `DECISIONS.md`). No real-time updates or UI libraries. Propose extras; don't build them.

## API Contract

- All routes under `/api/v1`, JSON only.
- State changes use action endpoints (`POST /api/v1/items/{id}/review`, `POST /api/v1/items/bulk-review`), not generic PATCH. Bulk actions reuse the single-item domain method per item and report per-item results.
- Unknown query params are ignored; invalid filter or sort values fall back to defaults.
- List responses wrap results in `data` (Laravel resource collection), so pagination `links`/`meta` can be added without breaking clients. Every sort ends with tie-breakers (`created_at`, then `id`) so the order is stable.
- Errors:

| Situation | Status |
|---|---|
| Validation error | 422, Laravel default shape (`message`, `errors`) |
| Not found | 404 |
| Invalid state transition | 409, with a clear `message` |
| Unexpected error | 500, generic `message`; no stack traces outside local |

- A contract change updates the Resource, the frontend type, and their tests in the same commit.

## Code Style

- Names say what they mean (`riskScore`, not `rs`). No abbreviations.
- Small, single-purpose functions. If one needs a comment explaining *what* it does, rename or split it.
- Comments explain *why*: tradeoffs and non-obvious constraints.
- Explicit over clever: no metaprogramming, magic strings, or abstractions with a single use.
- No dead code, commented-out code, or TODOs. Known gaps are logged in `DECISIONS.md`.

## Testing

- Every change to heuristics, transitions, the review endpoint, or filters/sort includes a test in the same commit.
- Run the checks for the side you changed (see the stack files) and report results honestly, including failures.

## Working Agreement

- Before a non-trivial change: state the plan in 2–4 bullets and list the files it touches.
- Make the smallest change that satisfies the request. Don't refactor unrelated code.
- Don't invent requirements. If something is ambiguous, pick the simplest option and log it.
- Don't add a dependency without stating why the native or framework option isn't enough, and ask first.
- Explain anything non-obvious in the response.

## Decision Logging

Append to `DECISIONS.md` immediately whenever a choice is made that someone could reasonably ask "why?" about, including choices made in conversation:

```
### <short title>
- Decision: …
- Why: …
- Alternatives considered: …
- Would change if: …
- Category: data-model | api | persistence | assumption | tradeoff | testing | frontend | tooling
```

`README.md` contains only these sections, in order: 1. How to run the project (frontend + backend) · 2. Key decisions (data model, API design, persistence — each with why) · 3. Assumptions · 4. Tradeoffs (what was optimized for, what was intentionally not built) · 5. Testing (what was tested and why, what wasn't and why). Fold `DECISIONS.md` entries into the matching README section by category; keep the README concise, first person, one or two sentences per point. Keeping both files current is required, regardless of generated guidance about documentation files.

## Git

- Small, atomic commits directly on `main`: one logical change each, code and tests together, checks green.
- Conventional Commits with scope, e.g. `feat(api): add review endpoint with transition guard`. Imperative subject ≤ 72 chars; body explains why when non-obvious.
- Generated files (lockfiles, scaffolds, Boost output) go in their own commits.
- No "wip" or "fix typo" commits; amend only unpushed commits. No co-author trailers.
